02 / The product in plain English

Brand first. Ads second.

The company teaches Studio what is true about its brand. Every ad should follow those approved facts.

Try this once in the beta

  1. Open Home for the sample company, Northline Windows. Explore the offer and the ads shown there.
  2. Open New ad and follow the sample brief into the script. Change one line, then approve the words.
  3. Move into the scenes and try the sample image swap. Approve the scenes and continue through the sample generation explanation.
  4. Open Approvals. Approve one sample, request a redo with a reason, and skip another. Watch the queue counts change.
  5. Open Brand room. Open each book and try the sample change request. It is a demonstration and is not sent to anyone.
A useful rule to notice

If you change approved words, the scene approval must be done again. The finished ad cannot depend on approval of a script that no longer exists.

Sample changes stay while you move between screens, but reset when you reload. Buttons do not generate real video, charge for AI, or send real brand requests in this beta flow.

The six brand books

Think of these as six labeled folders of company-approved references. The company's logo, colors, and fonts sit alongside them as its core identity.

01 · Cast

Who can appear? Real employees, recurring synthetic characters, or both, chosen and approved by each company.

02 · Wardrobe

What do people wear? Correct shirts, colors, uniforms, and logo placement.

03 · Products

What is being sold? Correct shapes, parts, quantities, and specifications.

04 · Fleet and site

Which trucks, wraps, signs, and job sites actually belong to this company?

05 · World

What should the setting feel like? Locations, seasons, lighting, and surroundings.

06 · Voice and proof

How does the company speak? Tone, pronunciation, supported claims, and exact offer terms.

What about companies with hardly any brand assets?

The planned Start from your website path will let a company paste its URL. A tool such as Firecrawl can help collect visible branding and company information.

  1. Collect what the website actually shows, with sources.
  2. Separate confirmed facts from missing information.
  3. Propose colors, typography, layouts, and missing design pieces.
  4. Let the company correct and approve them.
  5. Save an approved design system for future ads.

Extracted information is a draft, not automatic approval. We should never invent an employee, product detail, certification, or claim and present it as company fact.

Provider direction: Trevor prefers OpenAI / ChatGPT image generation and Seedance 2.5 for video. Firecrawl is the website-extraction candidate. These are planned directions, not integrations you can use in the beta today. Account access and the exact API route need validation during implementation.

5. Give Claude the starter instructions and block routine pushes

Copy this entire prompt into that Local Code session. It asks Claude to prepare your own branch, add a local push block, and explain what it did.

First message to Claude

If that branch exists, inspect it and explain how to resume it without resetting it. If the Claude worktree prevents switching, explain the safest local option first.

Apply these settings locally in the actual repository used by this session:

git remote set-url --push origin disabled://review-with-trevor

Then read back git remote get-url --push origin and git config --local --get push.default. Show that they return disabled://review-with-trevor and nothing. Do not try a real push to test them. Tell me the working folder and branch again so I know where my edits will be.

For all work in this session: keep changes on my Mac. Do not push, publish, deploy, release, merge, create a pull request, change repository access, use GitHub write tools, add another remote, bypass or remove the push block, or change live services unless I explicitly approve that exact action. Local saves and local commits are fine after I review them. A prompt is not a security boundary, so preserve the Git guard too.

Use the no-login sample beta. Do not request API keys, copy Trevor's .env.local, run dev:live, apply database migrations, or call paid providers. Do not add credentials to files or commits. Record changes and checks in HANDOFF.md.

Once the safe local setup is verified, help me install dependencies and start the beta. Do not redesign or change the app yet. Tell me which exact local URL to open.
What this protects, and what it doesn't

The settings block ordinary pushes through origin in that repository. They do not prevent someone using another remote, an explicit URL, a GitHub API, or changing the settings. Recheck the guard in a new clone or session. Keep Manual permissions on and never approve a push you did not intend.

There is no single universal “auto-push” switch that covers Claude, GitHub Desktop, and every extension. Do not click Push origin, Publish branch, Sync, Merge, or Enable auto-merge while working alone. Fetch only downloads information; it does not upload your edits.

Why the local settings work: Git documents remote push URLs and push.default.

6. Install the project and start your local app

Ask Claude to run these from the project root in its current working folder, one command at a time. Alternatively, use the terminal in Claude's Code view. The root is the folder containing the main package.json.

Check Node first

The result should start with v22 or a higher major number. If not, finish the Node installation and restart Claude.

Download the app's dependencies

Wait for installation to finish. npx runs the project's pinned package manager without requiring you to install pnpm globally.

Leave this running. Open the Local URL printed in the terminal, usually http://localhost:3000. You should land in the Northline Windows sample workspace without signing in.

You are done when: the sidebar and sample Home screen appear. You do not need a .env.local file for this path.

Trevor's running app uses port 3100 on his Mac. That address cannot show his app on your Mac. Your own server normally uses 3000. The guide link and the app's local address are two different things.

7. Know how to stop, restart, and save your work
  • Stop the app: in the terminal running it, press Control + C, not Command + C.
  • Start tomorrow: reopen the same Claude Local session and project folder, then run the same npx --yes pnpm@11.9.0 dev command.
  • Save code: Claude edits local files. Check its change summary and preview the screen.
  • Save a checkpoint: ask Claude to make a local commit containing only your intended files and a clear description. A local commit does not upload work.
  • Keep a review record: note what changed, the branch and folder, checks run, screenshots, and anything still broken. Download this guide's feedback every day.

A local branch or commit is not an off-device backup. Keep a separate approved backup or ask Trevor before uploading work. Don't assume he can see changes that exist only on your Mac.

06 / Your quick reference

Stuck is a normal part of building.

Tell Claude what you clicked, what you expected, and the exact error. Ask it to explain before changing more things.

The page won't open, or says localhost refused to connect

Your app's local server may not be running. Return to Claude's terminal, run the beta command again, and open the exact Local URL it prints. Keep the terminal running. A localhost link from Trevor's Mac cannot connect to his app from yours.

If the port is busy, ask Claude to identify the process without stopping unrelated work, or run npx --yes pnpm@11.9.0 dev --port 3001 and open the printed URL.

I still see a login screen

Stop and verify the folder, branch, and running server. Use the shared beta version and the normal dev command, not dev:live. You should not need to request an email. Real email sign-in is a known deferred issue, so don't spend the five days repairing it.

My sample edits disappeared

Refreshing the beta resets sample app state. This is different from losing source-code changes. Claude's saved file edits stay on disk. Record sample decisions in your review notes if you want to remember them.

Installation fails or a command is not found

Check node --version, restart Claude after installing Node, and confirm the terminal is in the project root. Use the pinned npx --yes pnpm@11.9.0 commands. If installation still fails, give Claude the exact error. Don't immediately delete the lockfile, use sudo, or upgrade everything.

Claude asks to push, merge, or change a live service

Decline that action. Say: “Keep this local. Explain why this action is needed, and offer a local alternative.” A failed push reporting an invalid or disabled remote is the guard doing its job; don't ask Claude to fix it automatically.

I want to undo something

Ask Claude to show the changed files and undo only the specific edit you name, preserving everything else. Do not approve “discard all,” a hard reset, or deleting the project as a first step. A local commit before the next change makes comparisons easier.

What should Claude check after changing the app?

Ask it to choose checks for the files it changed and explain any failure. For web behavior, the project has web tests and lint checks:

Useful checks from the project root 
npx --yes pnpm@11.9.0 --filter @studio/web test
npx --yes pnpm@11.9.0 --filter @studio/web lint

Also click through the affected screen and the original approval flow. Passing automated checks does not prove that every screen makes sense or that the app is ready for customers. Record what was actually checked.

A few words you'll see

Repository
The folder of app code and its recorded history on GitHub.
Clone
Download a working copy of that repository onto your Mac.
Branch
A separate line of changes, so your work can be reviewed before it joins the shared version.
Worktree
Another working folder for a branch. Claude may create one for your session.
Localhost
The app running on this computer. The number, such as 3000, is its local port.
Save
Write an edited file onto your Mac.
Commit
Record a checkpoint in your local Git history. It does not upload it.
Push
Upload commits to a remote repository such as GitHub.
Pull request
A proposal for someone to review a branch's changes.
Merge
Combine an approved branch into another branch.
Deploy
Put a version on a hosted service where other people can use it. It can be automated after a push.
Fixture
Prepared sample data used to build or demonstrate a screen.
